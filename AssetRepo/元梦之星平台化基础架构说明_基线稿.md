2025-12-16 元梦之星客户端基建平台化基础架构说明（讨论基线稿 - LiteProject/LiteCore/公共平台能力/GameFeatures 对齐版）

---

## 1. 架构目标与核心理念

**当前主要问题**：

- **开发效率与工程复杂度**：工程仓库体量巨大，拉取与构建成本高；玩法间逻辑耦合严重，复用往往通过复制粘贴完成；重复造轮子现象普遍，3C、ECA、任务、背包等通用能力存在多套实现。
- **发布效率与交付节奏**：集中构建、分支众多、合线困难，构建时间长；资源发布高度依赖脚本与人工操作（例如单一 GCloud Puffer 链路），灰度与回滚能力不足，线上干预速度慢。
- **线上质量与体验**：包体大、下载成本高，重复资源与“为少量资源拉整包”的情况普遍；玩法间状态相互影响，Bug 与性能问题（卡顿、内存抖动等）难以快速定位与归因。
- **架构演进与治理压力**：模块边界模糊，底层与基础模块耦合紧密，技术债累积影响 UE 升级与多端支持；资产与配置缺乏仓库视角与治理机制，监控与运营闭环薄弱。

**平台目标**：
在统一 UE 引擎版本之上，构建一套“最小化游戏工程（LiteProject） + 游戏特性插件库 + 公共平台能力 + 离散化资产仓库”的客户端基建平台，为不同玩法 MOD 提供标准化运行环境与工具链，支撑 MOD 生态和多平台交付。

在这一平台目标下，我们进一步约定：

- **LiteCore**：指代“最小核心代码层”，由一组 C++ 模块和基础 Lua 脚本构成，紧贴 UE 引擎，承载 MOD 运行期最底层的管理、配置与运行时能力，可被多个工程和 MOD 复用；
- **LiteProject**：指代“最小化游戏工程模板”，在 LiteCore 之上，一键为每个 MOD 生成的最小开发环境，除了工程骨架本身外，还包含工程必要的最小资源依赖以及关于该 MOD 本身的一些工程侧配置（如标识、版本、分类等）。

**核心理念**：

- **引擎之上，MOD之下**：引擎负责底层通用技术，LiteCore 负责对引擎做最薄的一层 Core 封装，平台在其之上提供工程骨架（LiteProject）、特性插件、平台接入与资产复用，MOD 只关注玩法实现。
- **运行时沙箱化**：每一个 MOD 运行在隔离的运行时沙箱中，避免污染全局配置与运行环境。
- **管理端化与云端化**：MOD 的注册、配置、版本与发布从“配置表 + 手工流程”升级为“管理端 + 云端服务”。

5. **云端全平台发布能力**




## 3. 第一层：UE 引擎层（引擎能力定制和扩展）

**职责**：

- 提供统一的渲染管线、物理、网络、IO 等引擎级基础能力；
- 统一 UE 版本（当前 4.26，规划兼容 UE5+ 的升级路径），保证所有工程（包括元梦之外的工程）都可以在同一套引擎上创建和运行；
- 在不破坏官方能力的前提下，为平台化和多端发布场景提供必要的引擎级扩展能力。

**组成**：

- 与 Epic 官方发布的 UE4.26 / UE5.x 保持能力等价；
- 可以按照官方的引擎示例创建可以在该引擎版本上编译和运行工程；
- 不方向依赖任何游戏工程代码；
- 引擎层的改动需要由专门的引擎/基建团队管控，并与 Roadmap 中的“引擎升级策略”绑定。

## 4. 第二层：四大模块（客户端基建核心）

### 4.1 最小化游戏工程（LiteProject）

#### 4.1.1 命名与分工对齐

- **LiteCore**：
  
  - 最小核心代码层，由 C++ 模块 / 子系统 + 基础 Lua Runtime 脚本构成；
  - 紧贴 UE 引擎，负责 MOD 运行所需的底层管理、配置与运行环境；
  - 面向多个工程和 MOD 复用，不绑定具体工程内容或资产。

- **LiteProject（最小化游戏工程）**：
  
  - 基于 LiteCore 之上的最小化 UE 工程模板；
  - 提供一个极简但可完整跑通的工程骨架（包含工程结构、默认关卡、入口逻辑和构建配置）；
  - 在 MOD 申请后由管理端一键生成，作为该 MOD 的最小开发环境，同时承载与该 MOD 相关的一些工程配置（如包名、命名空间、基础元数据等）。

> 直观理解：**LiteCore 是“代码内核”，LiteProject 是“最小可运行工程壳”**。任何一个 MOD，都是在 LiteProject 这类工程骨架之上，接入元梦基础模块和自身玩法逻辑后形成的。

#### 4.1.2 LiteProject 的定位

**定位**：

- 一个极简但“可完整跑通”的空工程模板，是所有 MOD 的基础运行工程；
- 在引擎 + LiteCore 之上，只引入工程运行所必需的最小内容（工程结构、启动关卡、基础 UI 壳等）；
- 包含该 MOD 必要的最小工程侧配置与资源依赖（例如 MOD 标识与描述配置、默认图标/占位资源等），这些配置由管理端在一键生成工程时写入；
- 不内置任何元梦基础业务（社交、活动、商业化等），即便完全不依赖这些模块，也能独立完成构建、下载和更新（例如俄罗斯方块这类完全独立的单机 MOD）。

#### 4.1.3 LiteProject 的关键能力

- **标准工程骨架**：
  
  - 规范化的工程目录结构（Source、Content、Config 等）；
  - 预置最小化的默认关卡 / 地图、GameInstance / GameMode / PlayerController 等入口类；
  - 与 LiteCore 中的运行时内核（生命周期、场景管理）完成接线。

- **MOD 容器入口定义**：
  
  - 在工程层面对 `IModEntry` / `IModBootstrapper` 等接口提供实现样板；
  - 约定 MOD 入口文件、配置位置和初始化顺序，让任何 MOD 在同一套启动协议下运行。

- **构建与配置模板**：
  
  - 提供最小化的打包 / Cook / 分包配置，以及多平台 Target 设置；
  - 集成 LiteCore 中的构建/安装器接口，使“构建 → 产物 → 安装/更新”成为标准链路；
  - 允许管理端通过模板参数化地生成不同 MOD 工程（命名空间、包名、图标等）。

- **统一的下载与更新流程（抽象能力，对 MOD 开发者可见）**：
  
  - 在 LiteProject 内预置一套标准的“版本检查 → 下载 → 校验 → 进入游戏”的启动流程与基础 UI 壳；
  - 流程内部仅依赖 LiteCore 暴露的抽象下载接口（如 `IDownloadService`），而不直接依赖 COS 或任何具体云厂商 SDK；
  - 默认情况下，该抽象接口由“公共平台能力”中的 COS 下载服务提供默认实现，未来可按环境 / 平台替换为其他实现；
  - 对 MOD 开发者而言，只需在工程配置中声明 MOD ID / 渠道 / 环境等参数，即可复用这套统一下载更新流程，而无需关心底层 COS 细节。

- **基础 UI 壳**：
  
  - 提供最小化的 Loading / 错误提示 UI（工程基础壳），用于支撑安装、加载、错误回退等流程；
  - 不绑定任何产品视觉或复杂交互，后续由元梦基础模块或具体 MOD 自行扩展。

#### 4.1.4 LiteCore 与 LiteProject 的边界约束

- **LiteCore 负责**：
  
  - 运行时内核：生命周期管理、场景/关卡管理、Tick/Timer 等；
  - MOD 容器与运行上下文（MOD Manifest 解析、上下文对象、沙箱边界）；
  - 构建 / 下载 / 更新内核（补丁 Manifest 模型、安装器、版本兼容检查等）；
  - 环境抽象层：日志/崩溃/监控接口、平台能力抽象、资源访问接口等。

- **LiteProject 负责**：
  
  - UE 工程层面的骨架结构与配置（工程文件、默认地图、基础入口蓝图/Lua 等）；
  - 将 LiteCore 的能力以“工程可用”的形式接线，形成可直接运行和调试的最小工程；
  - 对 MOD 团队暴露最少的一套“需要关注的胶水代码”和工程规范；
  - 对外呈现统一的下载 / 更新流程与 UI，但不承载具体的 COS / 云平台实现逻辑。

- **显式不属于 LiteProject 的内容**：
  
  - 任何元梦产品级基础模块：好友社交、活动、商业化、大厅等；
  - 通用玩法特性：ECA、3C、技能系统、AI 等，这些属于“游戏特性插件库”；
  - UGC 编辑器、运营管理端等工具；
  - 与云端策略紧耦合的复杂逻辑（灰度策略、多区域路由），这些属于“云端全平台发布能力”。

> 总结：**LiteCore 做“代码内核 + 能力抽象”，LiteProject 做“最小工程骨架与接线”，公共平台能力提供 COS 等平台实现，对 MOD 开发者只暴露抽象接口。在这三者之上才是元梦基础模块和各个 MOD。**

### 4.2 游戏特性插件库（丰富的游戏插件）

**定位**：

将玩法通用能力沉淀成可选插件库，为各个 MOD 复用（PPT 中紫色块“丰富的游戏插件”）。相比公共平台能力偏“SDK 接入 + 平台能力”，游戏特性插件库更关注“**玩法层的可复用能力**”，并从两个维度提供能力：

1. **平台通用玩法能力插件（Universal）**：
   - 如 Avatar 组装、3C（角色/摄像机/操作）、ECA 玩法规则引擎、技能 / 战斗基础、AI 框架等；
   - 独立于具体品类，提供“所有 MOD 都可以直接拿来用”的统一玩法能力。
2. **品类基底玩法能力插件（Genre）**：
   - 面向休闲跑酷 / 模拟经营 / FPS / RPG 等重点品类，提供一套“品类基底包”；
- 在复用通用玩法能力（Universal）的基础上，补齐该品类特有的玩法骨架（如跑酷的轨道/机关、经营的生产链、FPS 的武器/射击、RPG 的任务/成长）。

> 直观理解：公共平台能力负责“接平台、调 SDK”，GameFeatures 负责“打玩法基座”。两者共同为 LiteProject 和 MOD 提供能力支持。

#### 4.2.1 能力维度与划分

从平台化视角，我们将游戏特性插件库划分为两层：

- **Universal（通用玩法能力层）**：跨品类可复用的玩法基础能力，主要包括：
  - Avatar & 角色表现（骨骼装配、部件组装、时装穿戴等）；
  - 3C & Locomotion（移动、镜头、输入统一状态机）；
  - ECA / Rule Engine（事件–条件–动作规则驱动）；
  - Ability / Skill & Combat（技能 / Buff / 伤害结算等）；
  - AI & 导航（导航网格、行为树、感知等）；
  - 关卡流程 / 任务流（Checkpoints、关卡节奏控制）；
  - 通用交互（触发器、交互点、拾取等）。
- **Genre（品类基底层）**：在 Core 能力之上，为重点品类提供“半成品基底包”，如：
  - 休闲跑酷基底（Track/机关/节奏）；
  - 模拟经营基底（生产链/建筑/时间系统）；
  - FPS 基底（武器/射击/命中反馈）；
  - RPG 基底（任务/剧情/成长/装备）。

> 为避免“Core/Genre”命名引起误解，本节后续讨论中统一使用 **Universal（通用玩法能力）** 与 **Systems（跨品类玩法系统）** 这两个概念词。二者只是概念层的划分，并非真实模块名。

> 在实现与目录上，Universal 和 Systems 所有插件都**统一存放在 `GameFeatures` 目录下**，模块内部可以按 Core/System 等方式组织子结构，但对外模块名尽量不再带 `Core` 等后缀。

#### 4.2.3 跨品类玩法系统矩阵（Systems for Genres）

#### 4.2.4 边界与依赖约束（与 LiteCore / PlatformSDKs / 元梦基础模块）

为避免 GameFeatures 与其他层次形成循环依赖，本节确定以下约束：

- **与 LiteCore 的关系**：
  - LiteCore 提供运行时内核（生命周期、场景管理、资源访问等）和能力抽象（日志/监控/下载接口等）；
  - GameFeatures 只能依赖 LiteCore 暴露的抽象接口，**不反向依赖具体工程或 MOD 代码**；
  - 3C/ECA/Ability 等能力应以“插件 + 子系统”的形式挂在 LiteCore 之上，LiteCore 不承载具体玩法逻辑。

- **与公共平台能力（PlatformSDKs）的关系**：
  - GameFeatures **不得直接依赖外部 SDK**，只能通过公共平台能力暴露的接口使用账号、支付、数据上报等平台能力；
  - 品类基底包若需要 A/B Test、埋点、云游等能力，应通过 PlatformSDKs 对应域（如 Data & Telemetry、CloudGame）获取，而不是自己封装 SDK；
  - 在能力矩阵中，对于“强依赖平台能力”的 GameFeatures，需要显式标记依赖域，方便 Roadmap 对齐。

- **与元梦基础模块的关系**：
  - 元梦基础模块（好友、活动、商业化、大厅等）可以复用 GameFeatures 的能力（例如使用 Avatar/3C/ECA），但不反向“拥有”这些插件；
  - GameFeatures 只提供“玩法基础能力”，不内嵌任何具体产品逻辑（如具体的活动规则、商业化策略），避免后续被非元梦工程复用时产生耦合；
  - 对外暴露的接口以“通用概念”为主，例如“任务/奖励/关卡”，具体产品含义由元梦基础模块在上层组合实现。

#### 4.3.3 运维与效能工具域（DevOps & Diagnostics）

**定位与分层归属**：

- 运维与效能工具本质上仍属于“公共平台能力”层的一部分，由 `PlatformSDKs` 提供统一的插件和脚本实现；
- 与账号、支付等运行时能力不同，这一子域主要服务于**开发 / 测试 / 运维阶段**，在玩家视角下通常不可见；
- 在分层上，它们定义在本节（4.3 公共平台能力）中，但会在“全链路管理端化”中被管理端流程与流水线调用。

**能力类型划分**（与上表中的“运维 & 效能工具（DevOps）”域一一对应）：

- 自动化测试与录制回放：如 `GAutomator`、`UeInputReplay` 等，用于端到端用例执行和输入录制回放，支撑回归测试与巡检；
- 脚本 / 配置热更新与上传：如 `ScriptUploadTool`、`MoeLuaHotfixTool` 等，为开发/调试环境提供 Lua 脚本与配置的快速迭代能力；
- 运行时诊断工具：如内存泄露扫描、`UObject` 超限检测、ASAN 辅助工具等，为线上问题排查和稳定性治理提供支撑；
- 静态扫描与质量闸门：如 AICR 扫描等，为提测 / 发布前提供代码质量与规范的自动化检查能力。

**使用与约束原则**：

- 运行时代码与 DevOps 工具要在模块与依赖上**显式解耦**：工具模块不应被游戏特性插件或 MOD 直接依赖，避免工具逻辑进入正式发行包；
- 通过编译开关 / 配置开关控制工具启用范围：在开发/测试环境启用全部能力，在正式环境仅保留必要的监控/上报；
- 管理端的流水线（例如自动化测试、质量检查）优先通过统一的 DevOps API 调用这些工具，保证调用方式和结果输出格式的一致性。

> 简单理解：**公共平台能力不仅包含“对玩家可见”的运行时平台能力，也包含“对研发可见”的运维与效能工具域。前者直接支撑 MOD 运行，后者支撑平台化下的高效开发、测试和运维。**

### 4.4 离散化公共资产仓库

**定位**：  
建立一个真正可供所有 MOD 共享的资产中心（PPT 中橙色块“离散化资产仓库”），以“离散资产”为基本单元管理美术与音频资源，在**不依赖具体 MOD** 的前提下提供跨 MOD 复用能力，并通过更细颗粒度的打包与下载策略，避免“引用几个资源却被迫下载一个巨大包体”的情况。

#### 4.4.1 当前没有离散化资产仓库面临的问题

- **资源包粒度过粗，引用少量资源需要下载大包**：  
  - 现有资产通常按“大场景 / 大玩法 / 整包内容”打包，一个 MOD 只想复用其中少量角色 / 特效 / 音频时，往往被迫拉整包资源；  
  - 当一个 MOD 同时引用多个公共资源时，这些资源往往来自多个大包，叠加后对首包和增量下载的压力非常大。
- **公共资产不真正公共**：  
  - 同一角色、特效或音效在不同 MOD / 工程中各自拷贝和修改，难以统一修复与演进；  
  - 不同 MOD 可能同时存在多个版本的“相似资源”，包体和维护成本都很高。
- **强路径耦合与重定向链问题**：  
  - 资产引用强绑定目录路径，公共资源深挂在某个大工程下面，迁移到“公共位置”需要修正大量引用；  
  - UE 的 Redirector 链条会不断累积，增加 Cook/打包和运行时的复杂度与风险。
- **多端 / 多设备适配成本高**：  
  - 目前同一资源在不同设备（高端机 / 低端机 / 云游 / H5）上往往通过多套配置或多份资源实现，缺乏统一的 LOD / 变体管理；  
  - 难以做到“针对当前设备只下合适规格”的精细控制。
- **缺乏资产级治理与度量**：  
  - 资源没有统一的“仓库视角”：谁拥有、谁在用、版本如何演进、质量是否达标都不清晰；  
  - 改一个公共资源的影响范围难以评估，导致大家更倾向于“复制一份再改”，进一步放大问题。

#### 4.4.2 离散化资产仓库可以解决的问题

- **真正实现跨 MOD 复用与统一演进**：  
  - 通过“公共仓库 + 只读治理”，让通用角色、特效、音频等资产只在仓库中维护一份；  
  - 所有 MOD 通过引用使用，同步享受 Bug 修复与品质优化。
- **显著降低包体与增量下载成本**：  
  - 将资源颗粒度从“大包”降低到“单资产 / 小型资源组”，MOD 只需要为实际使用的资产付出下载成本；  
  - 当多个 MOD 引用同一资源时，终端只需下载一次即可被多个 MOD 复用，避免重复下载。
- **支持按设备 / 平台 / 场景的精细化 LOD 与变体策略**：  
  - 在仓库中统一管理同一逻辑资产的多套规格（高模 / 低模、多分辨率贴图等）；  
  - 结合设备/平台/场景信息，按策略选择合适版本，兼顾画质与性能/包体。
- **提升资产可治理性与可观测性**：  
  - 通过资源管理服务器，对资产建立完整的元数据、版本、依赖与引用关系视图；  
  - 可以在变更前看到哪些 MOD / 玩法在使用该资产，为评审与回滚提供依据。
- **为 UGC / H5 / VA 等场景提供稳定的资产基础设施**：  
  - 离散化仓库天然适合“按需加载 + 轻量分发”的场景，避免在轻量终端上被大型资源包拖垮体验。

#### 4.4.3 实现思路、关键技术点与对现有机制的影响

结合讨论，这里明确“引擎内部资源标识”与“资源管理层 GUID / AssetRepo”之间的边界，并对实现路径中的关键取舍进行说明。

- **资产标识与 Pak 元信息（不改引擎内部 GUID）**：  
  - 引擎内部的对象标识（`FName` 路径、`SoftObjectPath`、内部 GUID 等）保持不变，不在 AssetRepo 改造中直接修改；  
  - 公共仓库中的资源存放方式更偏扁平化：按目录 Cook 成若干 **小粒度 Pak**，每个 Pak 作为“离散资产组”；  
  - 在“资源管理层”引入 **Pak 级 GUID（PakGUID）**，将其视为该组资产的元信息：  
    - `PakGUID` 用于唯一标识一份公仓 Pak；  
    - 仓库记录 Pak 与 Pak 之间的依赖关系（例如“角色 A Pak 依赖 通用材质 Pak”）时，以 `PakGUID` 之间的关系来表达；  
  - Pak 内部的具体资产仍通过 UE 原生路径 / MountPoint+路径进行引用与加载；  
  - **资源管理侧（下载/挂载模块）需要认识 `PakGUID` 与依赖关系**：当为某个 MOD 选择加载一份公仓 Pak 时，需要根据 Pak 元信息中的依赖描述，递归解析出所有前置依赖 Pak，对依赖闭包内的 Pak 统一下载与挂载；  
  - 对于玩法代码 / 资产引用侧而言，仅需感知“路径与引用关系”，不直接与 `PakGUID` 打交道。

- **资源颗粒度、分包与 Patch 策略（小 Pak + 全替换）**：  
  - 对离散化资产仓库本身，优先目标是将 Pak 粒度控制在“足够小”的范围，使得 **修改一个 Pak 时可以直接整包重下，而不是引入复杂的二进制差量 Patch**；  
  - 这样可以：  
    - 简化 Patch 工具链与流程，避免 Patch 组合引起的 Pak 爆炸；  
    - 在仓库层面只需维护“当前版本 PakGUID → Pak 文件”的映射，而无需叠加多层差量；  
  - 对于非 AssetRepo 体系下的大包（例如主工程部分内容），仍然可以保留现有差量 Patch 流程，但不强制统一到离散化资产仓库的策略中；  
  - 在 Scope 文档中，相关工作体现在“分包/分组规范”和“Patch 策略调整”两个小任务中，会把“AssetRepo 范围内优先采用全包替换”的决策标明。

- **小 Pak 数量与文件系统 / PlatformPakFile 效率的权衡（重要风险项）**：  
  - Pak 粒度变小势必引入 Pak 数量增加的问题：  
    - 文件系统层面：过多小文件会带来寻址、打开句柄、IO 调度等开销；  
    - 引擎层面：`PlatformPakFile` / Pak 管理在索引、查找、挂载时，如果仍按“有限 Pak 数量”假设实现，可能在数百 / 数千 Pak 规模下出现性能问题；  
  - 因此，这里刻意将“**Pak 粒度 vs Pak 数量 vs 查找效率**”作为一个需要持续关注和验证的风险，而不是在文档中简单给出结论：  
    - 在设计时需要给出推荐的 Pak 大小和数量级区间（例如：资源域级别、按使用频率/更新频率分组等）；  
    - 需要评估并可能改造 `PlatformPakFile` 或其上层索引结构，使其在面对大量小 Pak 时仍然可以快速定位资源；  
    - 这一部分会在执行视图中以专门的技术 Spike / Benchmark 任务体现，而不是单纯认为“Pak 越小越好”。

- **资源管理服务器与元数据模型（以 PakGUID 为核心，侧重离线管理）**：  
  - 资源管理服务器聚焦“仓库视角”的离线能力：  
    - 以 `PakGUID` 为核心记录 Pak 的版本、依赖关系、所属资源域等；  
    - 维护 Pak 内资产清单（路径列表）、资产类型统计等信息，为管理端/运营端提供可视化视图；  
    - 管理“入仓、文件修改、审核、下线”等流程，并生成供构建/发布使用的 Pak 清单与依赖描述（Manifest）；  
  - 资产元数据与标签（类型、域、LOD/变体、适用设备/平台、所属团队、发布状态等）依然存在，但更多是 **Pak 级元信息 + Pak 内资产索引** 的组合，而不是为每个资产单独造一套全球唯一 ID；  
  - 运行期客户端不直接依赖资源管理服务器在线服务，而是消费构建/发布阶段生成好的 Manifest 与配置数据，按其中的 `PakGUID` 关系进行下载与挂载。

- **公仓挂载与工程透明性（不额外垫一层资源加载接口）**：  
  - 对工程业务层（GameFeatures、MOD 等）而言，引入 AssetRepo 后的理想状态是“**加载方式不变**”：  
    - 仍然通过 UE 的路径 / 软引用来访问资产；  
    - 不引入额外的 `IAssetRepository` / `IAssetLoader` / 自定义资源加载接口层，资产加载仍通过 UE 自带的 AssetRegistry / Streaming 机制，沿着资产引用链自动落到对应 Pak；  
  - 公共仓库的 Pak 通过 **独立的 MountPoint** 挂载到引擎中，例如 `/AssetRepo` 或更细粒度的前缀：  
    - 这样资产路径在引擎视角下仍是常规路径，只是来源 Pak 不同；  
    - 将来即便把公仓拆到独立工程或独立仓库，只要 MountPoint 一致，业务代码仍然可以无感知复用；  
  - 下载与挂载流程：  
    - 管理端与资源管理服务器在离线阶段负责为某个 MOD 生成“所需 PakGUID 列表 + 依赖闭包”；  
    - 运行期的下载/补丁模块依据该列表下载并挂载对应 Pak（MountPoint 固定），并根据 Pak 元信息自动补全前置依赖；  
    - 挂载完成后，MOD 内的资产引用即可像访问本地资源一样工作，整个链路对玩法逻辑是透明的；  
  - **客户端下载栈与 COS 能力的复用**：  
    - 客户端侧的下载/补丁模块本身复用“公共平台能力”中的下载与 Patch 能力（例如 `COSHelper`、`DownloadEngine`、`FileHostingClient` 等），离散化资产仓库不再自建独立下载栈；  
    - AssetRepo 通过 Manifest 告诉这套基于 COS 的通用资源下载管理层“需要哪些 PakGUID 及其依赖闭包”，由该层完成实际的数据下载与校验。

- **着色器编译与分发策略（Inline vs Native Shader）**：  
  - 公共仓库中大量资产会携带材质与着色器，对应有两种典型编译与分发方式：  
    - **Inline Shaders**：着色器代码随资产 Package 一起 Cook 和下发，使用和部署路径最简单，但会显著增大材质资产体积，从而放大对应 Pak 的大小；  
    - **Native Shader Library / ShaderCodeLibrary**：将编译后的着色器集中打包为独立的 Shader 库（常见于移动平台与多平台发布场景），可以减小单个材质资产体积，但需要额外管理 Shader 库的构建与分发；  
  - 如果公仓材质主要采用 Inline 模式，资产随着 Pak 下发即可，Shader 流程简单但需要关注“材质资源变大 → Pak 体积变大”的影响；  
  - 如果依赖 Native Shader / ShaderCodeLibrary，则需要仔细设计：  
    - 公仓资产对应的 Shader 代码如何在 Shader 库中分组与索引（按 PakGUID／资产域划分）；  
    - Shader 库如何与 Pak 一起增量更新（例如：某个公仓 Pak 升级时，对应的 Shader 段如何独立更新并与客户端已有 Shader 库兼容）；  
    - 不同平台（移动/PC/云游）是否需要针对公仓单独构建 Shader 库或 PSO Cache；  
  - 这一部分在当前阶段会以“技术预研 + 方案选型”的形式存在，短期内可以优先支持与现有 Shader 流程兼容的方案，并在后续版本中按资产规模与平台需求决定 Inline 与 Shader 库的组合策略。

- **对现有机制的影响与兼容策略（更新版）**：  
  - **对 Cook / 打包 / 补丁机制**：  
    - 需要新增“公仓 Pak”这一类分包规则，并在构建脚本中对其单独处理；  
    - 对 AssetRepo 范围内的 Pak，Patch 策略以“整包替换”为主，避免与现有差量 Patch 逻辑叠加后过于复杂；  
    - 可能需要对 `PlatformPakFile` 或其上层管理逻辑做性能优化，以适应更多小 Pak 的场景。  
  - **对现有内容工程与引用方式**：  
    - 原有基于路径的引用方式可继续使用，只是在部分公共资产迁移到公仓后，需要调整其路径以匹配新的 MountPoint；  
    - 为降低一次性改动风险，可以在过渡期通过 Redirector 或配置桥接的方式支持“旧路径 → 新路径”的迁移，但长期目标仍是清理多余 Redirector。  
  
  - **对开发与编辑流程**：  
    - 编辑器内资源使用习惯尽量保持不变，更多变化集中在“资产入仓 → 生成 Pak → 发布”的流水线与工具上；  
    - 美术/策划只需在导入/提交阶段遵循“公仓准入规则”（如命名规范、域划分、LOD/变体要求等），其余流程由工具与管理端承接；  
  - **对 Shader 与平台适配**：  
    - 在未完全引入 Shader 库分拆方案前，需明确公仓材质在现有 Shader 流程中的处理方式，避免因为拆 Pak 或更换 Shader 组织方式而意外增加 Shader 编译时间或运行期加载开销；  
    - 随着 UE 版本（例如 UE5+）对 Shader 管理的能力增强，需要评估是否可以复用或对齐官方的 ShaderCodeLibrary/PSO 管理模式来支撑公仓资产。

## 5. 第三层：全链路管理端化

**愿景标语（对应 PPT 中部绿色大条）**：
**“注册、创建、发布全链路管理端化”**

### 5.1 当前痛点（没有管理端化时）

- **MOD 配置创建与维护成本高**：
  - 依赖工程内配置表 + Git 分支进行协作，分支数量一多，频繁出现同一张表多分支修改、合并冲突；
  - 一旦处理不当，容易导致配置数据损坏或丢失，缺少可视化的变更记录和回滚手段。

- **从立项到上线的流程和知识高度分散**：
  - 开始、进行、上线一个 MOD 的流程散落在口口相传、分散的 wiki 或文档中；
  - 质量检查主要依赖各团队维护的 checklist，执行质量与个人经验强绑定，门槛高、效率低。

- **资源发布通道割裂**：
  - 当前资源发布主要依赖 `GCloud Puffer` 渠道；
  - 在引入基于 COS 的资源下载管理能力（含离散化资产仓库 `AssetRepo`）之后，如果没有统一控制面，线上发布能力无法沉淀到标准流程中。

### 5.2 管理端化要提供的核心能力

- **MOD 注册与工程初始化管理端化**：
  - 通过管理端注册 MOD 时，基于表单配置 MOD 基本信息、目标平台、依赖模块等；
  - 提供“**一键生成轻量级 Project**”选项：勾选后，管理端会基于 `LiteProject` 模板，在 `GameFeatures` / 配置等既有规范之上，自动生成对应的轻量工程作为开发环境（包含最小目录结构、基础配置、必要的 CI/构建脚本等）；
  - 确保不同 MOD 的工程结构与平台化基线保持一致，降低接入成本。

- **版本、环境与流程模板管理端化**：
  - 以 MOD 为核心实体，统一管理“版本、环境、发布状态”等信息；
  - 将“立项 → 配置 → 构建 → 验证 → 发布 / 回滚”固化为可视化流程模板，替代口口相传的隐性流程与手工 checklist；
  - 每个节点挂接具体工具或动作（例如构建、基础校验、资源检查等），由系统驱动流程推进。

- **资源发布管理端化（对接 COS 下载能力与 AssetRepo）**：
  - 与“公共平台能力”中的 COS 资源下载栈、离散化资产仓库 `AssetRepo` 对齐，管理端负责：
    - 维护某个 MOD / 版本所需的资源包（主工程资源包 + 公共仓库 Pak / Manifest）列表；
    - 以环境为维度（测试 / 预发布 / 正式），一键触发资源在 COS / CDN 上的发布、灰度和下线；
  - 长期目标是在管理端视图中，把“资源发布”的操作与 MOD 版本发布统一起来，从而摆脱对单一 `GCloud Puffer` 渠道的手工依赖。

> 说明：与 DevOps 域中的自动化测试 / 巡检工具存在天然协同，但在当前阶段，**自动化测试不会作为这一层的关键节点**，优先落地的是 MOD 注册 & 工程初始化、流程模板化和资源发布管理能力。

### 5.3 角色与前后层的关系

- 向下：
  - 依赖 `LiteProject` 提供的最小化工程结构和构建规范，用于一键生成轻量工程；
  - 依赖 `PlatformSDKs` 中的账户、支付、COS 下载、日志等公共能力；
  - 依赖 `AssetRepo` 的离散化 Pak 模型和 Manifest，以便在管理端编排资源发布。

- 向上：
  - 为策划 / 美术 / 运营 / 技术提供以 MOD 为中心的“单一入口”视图，统一查看版本、配置、流程进度与资源发布状态。

## 6. 第四层：MOD 运行时沙箱与元梦基础模块

这一层对应 PPT 中央大白框区域：左侧虚线框是“元梦基础模块”，右侧虚线框是“每一个 MOD 都是一个运行时沙箱（MOD1, MOD2, …）”。

### 6.1 元梦基础模块

**模块示例**（与 PPT 中图标保持一致）：

- 好友社交；
- 活动；
- 时装；
- 大厅；
- 基础系统；
- 商业化。

**当前存在的问题与重构动机**：

- **与底层边界不清、耦合度偏高**：部分基础模块直接依赖 `GameInstance`、全局单例或引擎子系统，对 LiteCore / 引擎做了跨层访问，MOD 在接入时往往需要了解底层细节，破坏“引擎之上、MOD 之下”的分层原则；
- **数据访问与流程协议分散**：例如好友数据、玩家 Profile、活动状态、支付流程等，既有实现中存在“直接读配置表 + 直接调 RPC + 约定俗成调用顺序”的混合方式，不同 MOD 或系统对同一能力的使用方式不一致，导致重复封装和错误风险；
- **缺乏清晰的 Service 化边界**：目前 MOD 想要使用基础系统能力（如好友列表、统一支付流程、统一返回大厅逻辑等），往往通过共享数据结构或直接调用内部模块函数完成，难以做到沙箱边界控制和接口级治理；
- **与运行时沙箱协同不足**：在单 Lua VM 架构下，如果基础模块向 MOD 侧暴露了过多内部状态或可变对象，很容易形成跨 MOD 的引用链和内存泄露风险，削弱了我们在 `6.2` 中设计的运行时沙箱能力。

**重构后的定位与原则**：

在最小化游戏工程（LiteProject）之上，由平台提供的一组“公共基础游戏模块”，但其对外暴露能力将尽量通过“Service 化”的形式提供，形成一条从元梦基础系统到 MOD 的受控访问通路：

- **清晰的分层定位**：
  - 引擎 & LiteCore 层负责运行时内核、生命周期、基础上下文与能力抽象；
  - 元梦基础模块层负责“好友、活动、大厅、商业化、基础系统”等产品级能力的实现与编排；
  - MOD 层不直接操作底层对象，而是通过基础模块暴露的 Service API 获取数据和发起通用系统调用。

- **通过 Service 向 MOD 提供受控能力**：
  - 在基础模块内部抽象出一组跨 MOD 统一的 Service 接口（概念上如 `FriendService`、`ActivityService`、`LobbyService`、`CommerceService` 等），对外只暴露稳定的 C++ / Lua API；
  - Service 负责封装底层数据模型（好友列表、活动状态、货币与商品、玩家基础信息等）和流程协议（如统一支付流程、统一回大厅 / 返回主界面流程），对 MOD 层屏蔽底层实现细节和平台差异；
  - Service 与 LiteCore 的运行时上下文对接（例如通过“当前 MOD 上下文”获取玩家会话信息、环境信息），避免 MOD 自己去访问全局单例。

- **与运行时沙箱的配合**：
  - 从运行时沙箱视角看，基础模块 Service 是 MOD 访问基础系统的“白名单入口”：MOD 默认不直接访问 `GameInstance` 或引擎级子系统，而是通过 Service 完成数据读取和动作发起；
  - Service 在 Lua 层的暴露方式需要与 `6.2` 中的沙箱策略对齐：只通过受控环境表暴露给对应 MOD，避免跨 MOD 共享可变对象，确保在 MOD 卸载时便于回收和清理；
  - 对于高风险能力（如支付、账号变更、全局配置修改），在 Service 层增加权限校验、限流和审计挂点，以便后续在管理端与监控体系中进行统一治理。

> 直观理解：**元梦基础模块负责“产品级基础系统的实现”，但对 MOD 暴露的是一组经过 Service 化的受控 API**。MOD 只通过这些 Service 使用好友、活动、大厅、商业化等能力，而不直接触碰底层实现细节，从而既满足复用需求，又为运行时沙箱和内存安全提供基础。

### 6.2 MOD 运行时沙箱

**概念**：
每一个 MOD 都是在“运行时沙箱”中运行的独立单元（PPT 中黄色盒子 MOD1～MOD5）。

**两类沙箱能力**：

- **配置沙箱**：对物理配置、渲染配置等引擎全局配置进行沙箱化改造，保证 MOD 的配置不会污染全局；
- **运行沙箱**：运行期间的改动在退出时可完全销毁，同时在 Lua 层尽可能将 MOD 运行限制在可控范围内。当前设计上区分两个阶段：
  - **短期（单 VM 软沙箱）**：MOD 与元梦基础系统共用同一个 Lua VM，通过为每个 MOD 创建独立的 Lua 环境表、限制可访问的全局 API、统一登记并在卸载时清理 Delegate/Timer 等引用、在加载/卸载前后记录 Lua 内存变化等手段，尽量隔离 MOD 的全局状态与内存增长；
  - **中长期（多 VM 演进方向）**：以“一部分高价值 MOD 拥有独立 Lua VM”为目标，在不直接修改 UE4.26 核心结构的前提下，对 UnLua 进行多虚拟机适配改造（引入 VM 管理器、将绑定/调用从单例 `lua_State` 迁移到按 VM 分发），实现按 MOD 或 MOD 组粒度的 Lua 运行沙箱。
- **技术注意事项（需要在实现阶段重点讨论）**：
  - 完全禁止 MOD 访问 `GameInstance` 或引擎级能力不现实，需要通过 API 裁剪和 Service 化方式间接暴露有限能力；
  - MOD 允许定义自己的单例与静态变量，但必须约束其生命周期，避免与元梦基础系统之间形成长期引用链，导致 Lua 内存无法回收；
  - 目前 UnLua 默认假设单一 Lua VM，多 VM 架构涉及 VM 生命周期管理、类型绑定复用、调试/热更工具链适配等一系列改造，需要单独立项评估可行性与成本。

**目标**：

- 保证多个 MOD 可以并存、快速切换，而不会在配置和运行状态上相互干扰；
- 在 Lua 层提供清晰的演进路径：先通过单 VM 软沙箱降低风险，再视 UnLua 多 VM 可行性逐步演进到更强的沙箱隔离。

## 7. 第五层：云端全平台发布能力

**位置**：
PPT 顶部蓝色横条“云端全平台发布能力”。

### 7.1 能力范围与发布单元模型

- **多平台发布**：支持 APP / PC / VA / H5 小游戏等多终端，按平台维度选择发布；
- **与大版本解耦**：在无 Native 修改的前提下，MOD 可以随时通过云端进行发布和更新，不必跟随主工程大版本；
- **灰度能力**：提供分批放量、版本回滚等灰度控制能力。

在此基础上，我们引入统一的 **“发布单元（Release Unit）”模型**：

- 一个发布单元由以下元素组成：
  - 某个 MOD 的版本（含依赖的元梦基础模块版本约束）；
  - 对应的客户端版本范围与目标平台 / 终端（APP / PC / VA / H5 等）；
  - 来自 `AssetRepo` 的 PakGUID 闭包（即该版本所需的所有公仓 Pak 及其依赖）；
  - 需要发布的主工程资源包 / 热更包（如有）。
- 发布、灰度、下线与回滚都以“发布单元”为最小操作粒度，而不是以“单个资源包”或“混杂的脚本 & 配置组合”为粒度。

### 7.2 管理端与云发布能力的整合

在“全链路管理端化”完善的前提下，云端发布能力并不是一个孤立子系统，而是以管理端为唯一入口、在后台驱动 COS / CDN / GCloud 等多种发布通道的统一控制平面：

- **统一发布流程**：
  - 在管理端选择某个 MOD 版本及其目标环境 / 渠道，组成一个或多个“发布单元”；
  - 按流程执行质量检查（人工 / 自动化）、资源检查、版本依赖检查等；
  - 生成对应的资源 Manifest（含公仓 PakGUID 闭包）和版本配置，并触发 COS / CDN / GCloud 等发布动作；
  - 记录发布历史与结果，支持事后追溯与审计。

- **与 `AssetRepo` 和 COS 下载栈的协同**：
  - 管理端基于 `AssetRepo` 的 Pak 模型与 Manifest，清晰列出某个发布单元所需的公仓资源；
  - 云端发布动作只是将这些 Pak 与 Manifest 放置到合适的存储位置（如 COS / CDN），客户端侧依赖公共平台能力中的统一下载栈完成实际下载与挂载；
  - 通过这一层解耦，发布层只关心“发布什么”和“发布到哪里”，而不关心客户端如何具体下载与加载。

- **与 MOD 沙箱 / 基础模块的关系**：
  - MOD 运行时沙箱与基础模块 Service 化提供了运行期隔离与受控访问能力，使得以“发布单元”为粒度进行灰度与回滚时，更容易做到“出问题只影响该 MOD / 版本”，而不是拖累整个主进程；
  - 在遇到严重问题时，可以通过管理端快速将某个发布单元“熔断”或回退到上一稳定版本，配合沙箱机制降低线上风险。

### 7.3 发布可观测性与运营闭环

- **发布过程可观测**：
  - 通过 COS / CDN / GCloud 的回调与状态上报，在管理端查看每个发布单元的发布进度与结果（成功 / 失败 / 重试等）；
  - 对关键动作（创建发布单元、修改灰度策略、执行回滚等）记录审计日志。

- **运行效果可观测**：
  - 依托 `PlatformSDKs` 中的数据埋点 / 监控能力，采集下载成功率、安装/挂载成功率、崩溃率、关键性能指标（帧率、内存、加载耗时等）等数据；
  - 按 MOD / 发布单元维度归集指标，在管理端提供一体化视图，为运营与研发决策提供依据。

- **运营闭环**：
  - 结合管理端流程与监控数据，支持基于实际表现动态调整灰度比例、提前结束 / 延长灰度、快速回滚等操作；
  - 长期目标是将问题发现、定位、处理与验证串成闭环，使 MOD 的迭代节奏真正逼近“线上服务”的迭代方式，而不是绑定在“主包大版本节奏”上。

## 8. 与 2026 基建 Roadmap 的对齐关系（简要）

- **Milestone 1**：聚焦“UE 引擎层扩展 + LiteCore + LiteProject + 基础工程结构调整”，对应本架构中的 **第一层：UE 引擎层（官方基线 + 元梦扩展）** 与 **第二层：最小化游戏工程（LiteProject）**；
- **Milestone 2**：游戏特性插件化与平台能力封装，对应 **游戏特性插件库 + 公共平台能力 + 运行时沙箱**；
- **Milestone 3**：离散化资产仓库建设，对应 **离散化公共资产仓库**；
- **Milestone 4**：云端全平台发布能力与更多微服务能力，对应 **云端全平台发布层 + 管理端化 + 服务器侧服务化**。
