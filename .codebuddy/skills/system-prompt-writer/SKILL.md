# 系统提示词编写器

## 概述

此技能用于帮助用户编写和修改高质量的系统提示词（System Prompt）。系统提示词是定义 AI 助手行为、能力和约束的核心配置，直接影响 AI 的输出质量和一致性。

## 核心原则

### 结构化设计原则

所有系统提示词必须按照以下六大模块进行组织，不可打乱顺序：

1. **角色（Role）** - 定义 AI 的身份、专业领域和人格特质
2. **原则（Principles）** - 规定 AI 的行为准则和价值观
3. **能力边界（Capability Boundaries）** - 明确 AI 能做什么、不能做什么
4. **SOP（标准操作流程）** - 描述处理任务的具体步骤和决策逻辑
5. **输出格式（Output Format）** - 规范响应的结构、格式和样式
6. **示例（Examples）** - 提供具体的输入输出示例供参考

### 编写质量原则

- **简明扼要**：用最少的文字表达清晰的意图，避免冗余和啰嗦
- **明确性**：避免模糊表述，使用具体、可执行的指令
- **一致性**：各模块之间逻辑自洽，不存在冲突
- **正向引导**：以正面示例为主，告诉 AI 应该怎么做，而非过多强调不该怎么做

## 工作流程

### 场景一：创建新的系统提示词

当用户需要从零开始创建系统提示词时：

1. **需求收集**
   - 询问目标 AI 助手的应用场景
   - 了解期望的专业领域和能力范围
   - 确认输出形式和格式要求
   - 收集典型使用场景示例

2. **方案设计与确认** ⭐
   - 根据收集的需求，设计系统提示词的整体方案
   - 输出方案摘要，包含：角色定位、核心能力、主要场景、输出风格
   - **使用 `AskUserQuestion` 工具向用户确认方案**，提供以下选项：
     - 确认方案，开始编写
     - 需要调整部分内容（说明调整点）
     - 重新设计方案
   - 用户确认后方可进入下一步

3. **结构化编写**
   - 按照六大模块顺序逐一编写
   - 每个模块完成后确认是否符合用户预期
   - 使用 `references/prompt_template.md` 作为起始模板

4. **验证与优化**
   - 检查各模块之间的一致性
   - 补充边界情况的处理说明
   - 添加具有代表性的示例

### 场景二：修改现有系统提示词

当用户需要修改已有的系统提示词时：

1. **结构分析**
   - 识别现有提示词中的六大模块
   - 评估各模块的完整性和质量
   - 找出缺失或薄弱的部分

2. **修改方案确认**
   - 根据用户需求，制定修改方案
   - 列出计划修改的模块和具体变更内容
   - **使用 `AskUserQuestion` 工具向用户确认修改方案**，提供以下选项：
     - 确认方案，执行修改
     - 调整修改范围
     - 取消修改
   - 用户确认后方可进入下一步

3. **定点修改**
   - 仅修改用户指定的部分
   - 保持未修改部分的原有结构和内容
   - 确保修改后各模块仍保持一致性

4. **结构保护**
   - 无论修改范围多大，都必须保持六大模块的完整结构
   - 如果用户的修改请求会破坏结构，应提出建议性方案

### 场景三：优化系统提示词

当用户希望提升现有系统提示词的质量时：

1. **质量评估**
   - 检查明确性：是否存在模糊表述
   - 检查完整性：是否覆盖所有场景
   - 检查一致性：各模块是否自洽
   - 检查可测试性：示例是否充分

2. **优化方案确认**
   - 根据评估结果，制定优化方案
   - 按优先级列出待优化项及具体改进措施
   - **使用 `AskUserQuestion` 工具向用户确认优化方案**，提供以下选项：
     - 确认方案，全部优化
     - 仅优化部分项目（选择具体项目）
     - 暂不优化
   - 用户确认后方可进入下一步

3. **针对性优化**
   - 根据评估结果提出具体优化建议
   - 优先处理影响最大的问题
   - 保持六大模块结构不变

## 各模块编写指南

### 1. 角色（Role）

角色模块应包含：
- **身份定义**：AI 是什么角色（如"资深技术顾问"、"专业翻译助手"）
- **专业领域**：擅长的知识领域和技能
- **人格特质**：沟通风格、语气、态度

```markdown
## 角色

你是一名[角色名称]，专注于[专业领域]。

### 专业背景
- [具体技能 1]
- [具体技能 2]
- [具体技能 3]

### 沟通风格
- [风格特点 1]
- [风格特点 2]
```

### 2. 原则（Principles）

原则模块应包含：
- **核心价值观**：最重要的行为准则
- **优先级规则**：当原则冲突时的处理方式
- **禁止事项**：绝对不能做的事情

```markdown
## 原则

### 核心原则
1. [原则 1]：[说明]
2. [原则 2]：[说明]
3. [原则 3]：[说明]

### 优先级
当原则之间存在冲突时，按以下优先级处理：
1. [最高优先级原则]
2. [次高优先级原则]
3. [一般原则]

### 禁止事项
- 禁止 [行为 1]
- 禁止 [行为 2]
```

### 3. 能力边界（Capability Boundaries）

能力边界模块应包含：
- **能力范围**：明确列出可以处理的任务类型
- **限制说明**：明确列出不能处理的任务类型
- **边界情况处理**：遇到边界情况时的应对策略

```markdown
## 能力边界

### 可以处理
- [任务类型 1]
- [任务类型 2]
- [任务类型 3]

### 无法处理
- [任务类型 A]：[原因说明]
- [任务类型 B]：[原因说明]

### 边界情况
当遇到以下情况时：
- [情况 1]：[处理方式]
- [情况 2]：[处理方式]
```

### 4. SOP（标准操作流程）

SOP 模块应包含：
- **流程步骤**：处理任务的具体步骤
- **决策点**：需要判断的关键节点
- **异常处理**：遇到问题时的处理流程

```markdown
## SOP

### 标准处理流程

1. **接收任务**
   - 理解用户需求
   - 确认任务类型
   - 评估是否在能力范围内

2. **信息收集**（如需要）
   - 询问 [必要信息 1]
   - 确认 [必要信息 2]

3. **执行任务**
   - [具体步骤 1]
   - [具体步骤 2]
   - [具体步骤 3]

4. **质量检查**
   - 检查 [检查项 1]
   - 检查 [检查项 2]

5. **输出结果**
   - 按规定格式输出
   - 必要时提供说明

### 异常处理
- 当 [异常情况 1] 时：[处理方式]
- 当 [异常情况 2] 时：[处理方式]
```

### 5. 输出格式（Output Format）

输出格式模块应包含：
- **格式规范**：输出的结构和格式要求
- **内容要素**：必须包含的信息
- **样式指南**：语言风格、格式偏好

```markdown
## 输出格式

### 标准输出结构
```
[结构模板]
```

### 必要要素
每次输出必须包含：
- [要素 1]
- [要素 2]
- [要素 3]

### 格式规范
- 使用 [格式要求 1]
- 遵循 [格式要求 2]
- 避免 [格式禁忌]
```

### 6. 示例（Examples）

示例模块编写原则：
- **以正向示例为主**：提供 2-3 个典型使用场景的正确示例
- **覆盖常见场景**：示例应覆盖最常见的使用情况
- **简洁具体**：每个示例应简短但足够说明问题

```markdown
## 示例

### 示例 1：[常见场景名称]

**输入：**
[具体输入]

**输出：**
[期望输出]

### 示例 2：[常见场景名称]

**输入：**
[具体输入]

**输出：**
[期望输出]

```

## 资源文件

### references/prompt_template.md

提供完整的系统提示词模板，可作为新建提示词的起点。包含六大模块的空白结构和填写指引。

使用方法：
- 创建新提示词时，读取此模板作为起始框架
- 根据用户需求逐个模块填充内容

## 注意事项

1. **简明扼要**：每个模块内容精炼，避免冗长描述，用最少文字表达清晰意图
2. **结构完整性**：确保最终输出包含完整的六大模块
3. **顺序一致性**：六大模块顺序不可更改：角色 → 原则 → 能力边界 → SOP → 输出格式 → 示例
4. **正向引导优先**：示例部分以正面示例为主（2-3个），避免负面示例和边界示例
5. **中文输出**：所有提示词内容均使用中文编写
